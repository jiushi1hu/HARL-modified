# 检查点保存修复说明

## 问题与修改

原训练循环只在 `update % eval_interval == 0` 时保存模型。当训练共 36 轮而间隔为 50 时，不会生成任何检查点。

现在 `CascadeReservoirRunner.run()` 的保存顺序为：

1. 第一次 rollout 之前，将本次运行的起始模型保存到 `models/initial/`。
2. 每隔 `train.save_interval` 轮，将最新模型保存到 `models/`，覆盖上一次定期模型。
3. 最后一轮训练完成后，无论是否达到保存间隔，始终保存到 `models/`。
4. 保存发生在评估之前，评估报错不会丢掉刚完成且已保存的更新。

`save_interval` 与 `eval_interval` 分开，YAML 默认都是 50。旧 JSON 配置没有 `save_interval` 时，使用原 `eval_interval` 作为保存间隔，初始和最终保存仍然生效。
关闭 `use_eval` 不影响保存。最后一轮与定期间隔重合时只保存一次。

## 文件与语义

每个检查点包含已有接口保存的五个 Actor、Reward Critic、全部 Constraint Critics、各 ValueNorm、lambda 状态和观测编码文件；另外保存：

- `config.json`：本次运行配置。
- `checkpoint_metadata.json`：run_start/periodic/final、当前运行内完成的轮次和采样步数、来源模型目录、观测编码。

`models/initial/` 不随后续训练覆盖。若从旧模型开始，本目录代表本次运行的起点，不应称作随机初始化模型，来源记录在 `source_model_dir`。
最新训练后模型仍直接位于 `models/`，保持现有 `model_dir` 加载接口。
本次保存并未增加优化器、随机数和环境状态，因此它是模型评估/权重加载检查点，不支持逐位一致的断点续训。轮次只表示本次运行完成的更新数。
多个权重文件不是整体原子替换，请在保存完成后加载。完成元数据最后写入；失败写入不会保留上一次的完成元数据。

## 验证

按顺序运行并通过：

1. `python -m examples.test_cascade_reservoir`：Step 1。
2. `python -m examples.test_cascade_reservoir_step3`：包含 collect 的 Step 2/3。
3. `python -m unittest examples.test_cascade_checkpoints -v -f`：5 项回归测试。

新增测试使用真实短 rollout、物理环境、网络和优化器，验证：

- 1 轮训练且保存间隔 50、评估关闭时，起始/最终模型都存在。
- 起始 Actor 权重未被覆盖，最终 Actor 确实发生更新。
- 五个 Actor、全部 Critics、ValueNorm 和 lambda 均可重新加载并与内存值一致。
- 定期保存独立于评估，最后一轮不重复保存。
- 评估失败前最终模型已经保存。
- 保存失败恢复原目标路径，不写完成标记。
- 旧配置兼容，非法保存间隔报错。

修改的 Python 文件通过 AST 语法检查。

## 对当前运行及后续评估的影响

本修复只作用于重新启动后加载新版代码的运行，不能补救旧进程已经加载的保存逻辑。本次没有停止、重启或注入旧训练进程。
当前只完成保存问题修复；没有改变 gamma、预算或安全算法，也没有启动另一轮正式训练。

已经核对现有 `runner.eval()`：使用 deterministic=True，经同一 SequentialSampler 顺流采样，持续运行到环境 episode 结束；并非只评估一个 rollout 长度。
后续应提供独立评估入口，分别加载 `models/initial/` 与 `models/`，调用 `prep_rollout()` 和完整周期评估，全程不调用 `run()`/`train()`。目前仍不能声称已经完成训练后模型的三年对照实验。

如后续使用旧实验 config.json 重新训练，应指定新的实验名，并可显式传入 `--save_interval 1` 每轮保留最新模型。无需为此修改物理参数或论文公式。
